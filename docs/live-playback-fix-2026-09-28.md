# 虎牙周期性闪黑与 macOS 系统播放信息：调查及修复报告

日期：2026-09-28

发布版本：栖流 Qiliu 1.4.1

用户提供的复现房间：https://www.huya.com/196645

## 1. 结论

这次发现了两个相互关联、但并非同一个因果链的问题：

1. **闪黑来自播放器的续接方式。** 实测虎牙 HS 线路的一次 FLV HTTP 连接在约 119.7 秒时正常结束。旧代码虽然提前取得了新地址，但没有提前加载新画面；旧连接结束后仍然先销毁播放器、清空视频元素，再建立下一次播放，因此出现黑屏窗口。
2. **系统进度条来自错误的直播展示语义。** macOS 从视频元素读取到的是不断增长的有限媒体时长，而应用没有明确提供直播元数据和控制动作。这使系统把已追加的直播缓冲当成可定位的媒体时间轴显示。

因此，不能理解为“macOS 进度条走满导致了黑屏”。二者共同反映了当前有限连接及其缓冲的结束；直接导致画面清空的是应用的重建流程。隐藏进度条本身不会修复闪黑。

修复把虎牙连接轮换改成“旧画面继续播放 → 下一条连接静音加载 → 新画面准备好 → 交接 → 释放旧连接”，并独立配置系统播放信息。

## 2. 问题表现和影响范围

用户观察到原生“正在播放”面板中时间不断增长，接近尾端时应用短暂黑屏，然后继续直播；虎牙尤其频繁，其他直播源不明显。系统面板同时缺少房间封面、副标题，并显示不适合该应用的进度和跳转控件。

此次修复针对虎牙正在直播的 FLV 连接。HLS、回放和其他平台仍采用各自的连接及恢复策略；不能由一个房间的一次测量推断所有虎牙 CDN 都固定在同一秒数断开。

其他平台不容易出现相同周期，合理解释是它们的协议、连接生命周期和服务端行为不同，较少触发同一条 EOF 重建路径。此次没有进行所有平台的等时长对照实验，因此这部分是机制解释，不是对所有平台的实测结论。

## 3. 如何定位原因

### 3.1 真实网络测量

2026-09-27 对用户房间 196645 的 HS 原画 FLV 连接进行持续读取：

| 指标 | 结果 | 说明 |
| --- | --- | --- |
| 读取结束时间 | 约 119.7 秒 | 收到正常 EOF |
| 接收字节数 | 22,885,042 | 一次连接的累计数据 |
| 最大数据块间隔 | 647.5 毫秒 | 该次采样没有秒级断供 |
| 间隔 ≥ 1 秒的次数 | 0 | 不支持“这次是持续网络停顿”的解释 |

测试观察的是连接和字节到达情况，不能单独证明每一帧都已正常渲染，也不能揭示服务端为什么选择结束连接。确定的是：直播仍可重新取得有效地址，但这一条连接已经结束。

复现命令：

```bash
SIMPLE_LIVE_HUYA_TEST_ROOM=196645 \
SIMPLE_LIVE_HUYA_MEASURE_SECONDS=135 \
cargo test --manifest-path src-tauri/Cargo.toml \
  measures_current_huya_flv_chunk_gaps -- --ignored --nocapture
```

需要房间处于直播状态且能访问对应平台；房间转为回放时，该测量不能代替直播验证。报告不保存临时签名播放地址或凭据。

### 3.2 旧代码的实际执行路径

关键文件：`src/playback-supervisor.ts`。

旧版约 100 秒时只调用解析器取得下一次有效播放 URL，并保存为待续接信息。该动作避免重新等地址，但没有创建下一条媒体连接、缓冲音视频或准备解码器。

收到 `mpegts.Events.LOADING_COMPLETE` 后，流程仍会进入：

```text
handleMpegtsLoadingComplete
  → connect（即使标记为静默续接）
  → playUrl
  → destroyPlayers
  → video.pause()
  → video.removeAttribute("src")
  → video.load()
  → attach 新播放器
  → video.play()
```

从清空 `src` 到新播放器输出画面之间，旧画面已无法继续显示。这就是“静默”更新状态文字却仍然闪黑的原因。

### 3.3 系统进度为何随直播增长

FLV 由 mpegts.js 转换后追加到 MSE。此时视频元素的有限时长可能随收到的数据增长，它描述媒体缓冲时间轴，不是直播节目的完整时长，也不是已抓取的分片数量。

应用原先没有独立配置 Media Session，系统只能使用视频元素的默认信息。播放进度追上当前连接的末端，与连接结束后的重建发生在相近时间，产生了“进度条满了就黑屏”的视觉关联。

## 4. 修复设计和实现

### 4.1 提前加载下一条虎牙连接

播放约 100 秒后，使用 Rust 解析器重新取得当前线路及所需画质的有效签名 URL。创建第二个 video 元素和对应 mpegts 播放器，保持静音和不可见，让它实际接收并解码；此时旧元素继续承担画面和声音。

交接须同时满足：

- 已收到解码画面的 `requestVideoFrameCallback`；旧浏览器不提供该接口时，使用 `playing` 事件作为兼容判断。
- 新元素处于播放状态。
- 新元素当前播放位置之后至少有一秒连续可播缓冲。

准备就绪后，解绑旧事件、暂停旧元素，将音量和静音设置转交给新元素，切换可见画面及主播放器引用，最后销毁旧播放器。主界面的点击播放和音量事件也随元素更换而重新绑定。

这段时间会短暂存在两条连接和两个解码器，增加一些网络与解码开销；代价换取避免“先卸载再等待画面”的空档。新连接对应直播的新时间轴，交接不承诺逐帧连续，也不承诺音视频内容完全无跳跃。

### 4.2 失败、取消与状态变化

- 下一条连接准备失败：保留前台播放器，约五秒后重试，不因准备失败立即清空健康画面。
- 连接提前 EOF：立即启动同样的准备流程，继续利用旧缓冲和最后画面。
- 暂停、停止、换源、恢复流程：取消待交接连接并释放临时播放器。
- 异步解析返回时：检查取消标记和播放代次，过时响应不能接管新房间。
- 房间转为回放或下播：回到正常解析流程，不强行按 FLV 直播交接。
- 正常轮换独立记为续接，不计入故障重连或换线次数。

后台准备并不替代真实断网、无法解码等故障的恢复策略；网络中断时间超过缓冲时，仍可能出现等待。

### 4.3 系统播放信息与控制

新增 `src/live-media-session.ts`，由主界面同步房间和播放状态：

| 信息 | 提交给系统的内容 |
| --- | --- |
| 主标题 | 栖流 · Qiliu |
| 副标题 | 直播间标题 · 主播名 |
| 封面 | 房间封面，主播头像作为备用候选 |
| 动作 | 注册播放与暂停；清除定位、快进、倒退、上一项、下一项和停止处理器 |
| 时长 | 优先提交 Infinity；旧 WebKit 拒绝时提交零时长作为兼容展示 |

本机原生 WebKit 实测拒绝 Infinity，但接受零时长。这个兼容值只作用于系统展示，没有把视频文件长度改为零，也没有改变实际播放缓冲。HLS 真直播另外设置 `liveDurationInfinity`。

暂停和继续使用明确的 `setPaused(true/false)`，避免重复收到播放指令时误触发“切换”而反向暂停。暂停还会取消待交接准备，防止后台画面稍后自行替换前台。

### 4.4 房间封面与更新频率

后端独立传递 `coverUrl`：虎牙使用房间截图／封面，Bilibili 使用房间封面／关键帧，斗鱼使用房间图片，抖音使用直播封面。前端将 HTTP 图片升级为 HTTPS，并为虎牙实际使用的 `*.msstatic.com` 封面域名补齐 CSP 许可。

元数据只在标题、主播、封面或头像变化时重建。播放统计每秒更新不再重复触发封面请求。

macOS 系统面板的卡片尺寸、排版和封面最终占用面积由系统控制，网页无法按像素指定。当前实现提交了房间封面，但不声称已把系统卡片强制缩成截图中的其他应用样式。

## 5. 验证结果与边界

### 自动化验证

`npm run check` 全部通过：58 项前端测试、36 项 Rust 测试；11 项需要实时平台环境的网络测试默认忽略。TypeScript/Vite 生产构建及 `git diff --check` 通过。

新增回归覆盖：准备期间不暂停／清空旧播放器、画面与缓冲就绪才交接、暂停后过时响应不能交接、准备失败保留旧播放器、房间变为回放时退出直播交接，以及系统元数据和旧 WebKit 时长兼容。

### 实际网络及原生播放器

- 用户房间 196645 在直播期间，原生 WKWebView 连续完成三次同线路交接；现场统计换线零次，采样掉帧零。
- 2026-09-28 该房间变为回放后，续接观测改用正在直播的 691406。原生播放器 62.77 秒采样跨过一次交接，记录 3,678 次前台画面回调，最大回调间隔 278 毫秒，结束时仍在播放。
- 虎牙真实封面加载成功，尺寸为 1920×1080，控制台没有封面 CSP 错误。
- 键盘暂停显示 PAUSED，继续恢复 LIVE。
- 测试结束已恢复用户房间 196645，当时显示“微竞-浪D · 录像回放”。

这些结果证明新续接路径能在原生播放器中工作；278 毫秒的最大间隔也说明不能将它写成“零卡顿、无任何帧间隙”。

### 尚未完成的验收

1. 当前自动化工具无法读取 macOS 原生“正在播放”面板，因此尚未直接确认进度条、跳转按钮已消失，也未直接验证系统菜单按钮触发的暂停／继续。API 调用成功与模拟测试通过不等于系统菜单视觉验收。
2. 封面最终尺寸和裁切由系统决定，仍需在实际面板观察。
3. Windows 与 Android 发布构建不等于对应设备上的长时间播放验收；本次没有完成这两类设备的直播实测。
4. 一次 HS 连接的正常 EOF 和有限次数的续接采样，不能保证其他 CDN、网络、直播状态下均无中断。
