# 虎牙缓冲与重复片段回归修复

日期：2026-10-18

## 原因与现场证据

本机播放日志在 2026-10-18 01:30–01:32（日本时间）记录：HLS 清单连续出现 `levelLoadError code=0`，最后成功清单结束后，播放缓冲耗尽于 159.99 秒。软恢复读取仍停留在 158.03 秒的 `liveSyncPosition`，未检查方向就向后跳转。约两秒旧画面播完后再度缓冲，这一循环重复发生。每次倒退和重播都可能重置进度监测计时，延迟正常故障恢复。

`code=0` 只能证明 WebView 请求失败，不能单凭该状态断定签名过期、CORS 或网络故障。后续 Rust 解析重试明确收到多条 HLS CDN HTTP 403。清单持续失败的外部原因尚未确定。

## 修改

- 虎牙默认恢复 `resolve_live_stream` 的 HTTP-FLV 路径与已有预热续接。直播回放仍由后端返回 HLS；保留可续签 HLS 的后端和加载器实现，待原生长播验收后再评估默认启用。
- HLS 软恢复仅接受比当前位置至少领先 1.25 秒的有限同步位置；旧位置、相同位置和无效位置不再触发 seek 或重启加载，允许卡顿超时进入正常重连。
- 直播时间检测保留已播放到的最远位置，向后跳转及未超过该位置的旧媒体时间不再更新媒体进度计时。新播放器和 FLV 交接仍建立各自的媒体时间基准，录像回放的向后定位保持原有行为。

## 验证

- 修复前新增回归测试出现 6 项预期失败，涵盖默认 HLS 不可用、同步位置回退、无效追赶及恢复计时。
- 修复后完整 `npm run check`：99 项前端测试、58 项 Rust 测试通过，13 项实网测试默认跳过；TypeScript/Vite 生产构建通过，保留原有包体积提示。另覆盖录像回放向后定位的兼容行为。
- 额外运行两个真实网络测试，房间 `691406`：FLV 返回成功及 `video/x-flv`；HLS 新旧签名清单可读取，媒体序号相同，分片均返回 HTTP 206。后者只证明此时续签可用，不证明持续播放稳定。
- macOS 原生 WKWebView：构建并运行本地 debug `.app`，房间 `691406`、HS 线路、原画档位、1920×1080。日本时间 10:34:08–10:38:08 共 41 次约 6 秒间隔的心跳样本，跨两次预热续接，所有样本 `readyState=4`、掉帧计数为 0，最低前向缓冲约 6.7 秒。原生界面确认“直播接收正常”“同线路续接 2 次 · 换线 0 次”，未发生故障重连。
- 以上是约 4 分钟的原生播放与续接采样，支持此次回归修复；未做逐帧录像比对，也不代表 Windows/Android 长播或所有房间、网络条件均已验收。未替换 `/Applications` 中的安装版或发布新版本。

本地原生测试版：`src-tauri/target/debug/bundle/macos/栖流.app`。
